## 结论

| 问题 | 结论 | 首期确定方案 |
| --- | --- | --- |
| Python 3.14 + Pydantic 是否可行 | 可行；使用 Pydantic V2，不使用 V1 | 标准 CPython 3.14.x、Pydantic V2、asyncio |
| 管理和网关是否必须拆成服务 | 不必；职责应分开，首期部署合并 | 同一服务、一个 ASGI 进程，内部管理/网关模块分工 |
| 是否必须增加数据库服务 | 不必部署独立数据库服务；可靠登记与凭据撤销需要持久化 | 服务器 SQLite；客户端少量配置文件 |
| Redis 是否必需 | 首期不必需 | 活跃连接和短期状态留在进程内存 |
| 能否全部只依赖 Python | 服务与客户端可以用 Python；执行工具仍有外部运行时 | Playwright 原生服务与 Appium 按需使用 Node.js、浏览器及设备工具 |
| 是否需要面向某一种调用者封装 | 不需要 | 保留原生协议/API；二次封装由调用方选择 |
| 首期容量如何规划 | 以轻量控制连接和活跃执行分别制定目标，未压测 | 100 用户，按每人 1 个在线客户端估算；10 个轻量并发执行 |

Python/Pydantic 的结论基于官方支持说明、发布元数据和 wheel 核验，**不是完整依赖组合或实际驱动执行已经通过**。详细版本与限制见[技术栈可行性](../design/Python3.14技术栈可行性.md)。

## 已确定的最小实现

```text
Hub：   Python 3.14 + Pydantic V2 + FastAPI/Starlette + Uvicorn
        管理 API 与连接网关同进程
        SQLite 保存登记/凭据/会话元数据，内存保存活跃连接

Node：  Python 3.14 + asyncio + websockets
        主动连接服务器，探测本机资源，管理执行子进程
        本地保存节点身份和配置

执行：  Playwright 原生服务/已有浏览器桥接、HTTP 客户端
        Appium + 对应驱动 + ADB 或 WDA
```

首期采用一个服务器实例、一个 ASGI Worker；不额外引入 Redis、消息队列、工作流引擎或数据库服务器。外部执行工具按节点实际启用的能力安装，不要求每台节点安装全部工具。

首期容量目标为 **100 用户、10 并发执行**，容量估算按每名用户 1 个在线客户端计算；同一用户的多个在线节点按实际连接数累计。参考 Linux 服务器约 2–4 vCPU、4–8 GB 内存，浏览器和设备执行工具在客户端运行，截图、录像等重流量另测。这些数字是用户确认的规划与压测目标，不是已经验证的上限或 SLA，详见[最小实现与验证计划](../design/最小实现与验证计划.md)。

## RunBridge 对外提供什么

- 访问凭据：节点所有者提供对接码，服务验证对应节点和资源的使用许可。
- 查询：节点在线状态、资源准备/占用、工具版本、支持协议和限制；API 与 CLI 使用同一数据合同。
- 执行接入：受保护的 Playwright/Appium 原生协议或明确声明覆盖范围的工具接口。
- 通用运行约定：资源归属、会话释放、断连、错误、事件与输出获取。

RunBridge Hub 管理注册、许可与网关，RunBridge Node 管理本机资源，两者不依赖外部调用方的业务数据或内部代码。
