# RunBridge 最小实现与验证计划

[文档导航](../README.md)

**本文件是用户确认后的首期实施基线。** 范围、技术栈、部署、存储和容量规划已确定；具体接口字段、依赖锁定及执行细节在对应阶段落实。当前已完成 R0/R1，以及 R2 的资源/会话部分和 R3 受管理 Chromium 原生执行。首批仅接入 Playwright，独立 HTTP 与其他工具保留后续路线；当前实现见[执行架构](../architecture/Playwright执行与会话管理.md)，证据见[阶段验收](../project/Playwright阶段验收记录.md)。

## 1. 首期实现边界

| 内容 | 首期选择 |
| --- | --- |
| 服务拓扑 | RunBridge Hub：一台服务器、一个 ASGI Worker，管理/网关分模块 |
| 语言与模型 | 标准 Python 3.14.x、Pydantic V2、asyncio |
| HTTP/WebSocket | FastAPI/Starlette、Uvicorn、已锁定的 WebSocket 库 |
| 持久化 | SQLite 保存节点、访问许可及会话元数据 |
| 即时状态 | 内存中的活连接、资源占用与路由 |
| 客户端 | RunBridge Node：Python 常驻程序与 CLI，本地身份/配置文件 |
| 连接结构 | 每节点一条控制连接，执行会话使用独立出站隧道 |
| 在线容量规划 | 100 用户，按每名用户 1 个在线客户端估算 |
| 并发执行规划 | 10 个轻量执行会话，重流量另测 |
| 执行接入 | HTTP、受管理 Chromium 原生协议、一个已有浏览器授权路径、Android |
| 后续专项 | iOS、更多浏览器、客户端打包和多实例 |

首期不加入 Redis、独立数据库服务器、消息队列、通用工作流引擎、离线动作队列或透明恢复原生对象。已有可用部署设施可以复用，但它们不成为方案成立的前提。

## 2. 实施阶段

| 阶段 | 工作 | 验证 |
| --- | --- | --- |
| R0：版本准备 | uv 锁定 Python/Pydantic/WebSocket 候选，匹配执行运行时 | 完整依赖解析、目标 wheel 和最小导入/连接；不能只读元数据 |
| R1：登记与查询 | 稳定身份、节点接入、访问码、CLI/API、能力快照、SQLite | 错误/撤销凭据、重连和服务器重启后记录仍正确 |
| R2：会话与 HTTP | 资源申请/释放、占用冲突、本机 HTTP、技术错误 | 服务器不可直接访问的服务，由节点请求并返回准确结果 |
| R3：Playwright 原生路由 | 配套原生浏览器服务、获授权协议端点 | 官方 SDK 对象链、参数、事件、文件和关闭行为 |
| R4：已有浏览器 | 已实施 Chrome 固定 CDP 端点、整个实例授权 | 原页面/登录复用、资源许可和断开存活；当前结果见[R4 验收](../project/R4Chrome复用验收记录.md) |

R0 先确认版本，尤其不能将当前 npm Playwright 1.64.0 与 Python 1.63.0 默认混用。当前两侧已锁定 1.63.0，并完成实际 Chromium/官方 SDK 验收；其他候选记录保留原核验时点。

## 3. 核心验收场景

| ID | 场景 | 通过条件 |
| --- | --- | --- |
| N01 | 独立使用 | 普通脚本/CLI 能完成登记、查询与执行接入，不依赖任何外部业务系统 |
| N02 | 凭据范围 | 错误码、其他节点 ID、已撤销许可被拒绝；日志不默认输出秘密 |
| N03 | 身份重连 | 原节点可重新认证，伪造请求不能覆盖其他节点登记 |
| N04 | 状态新鲜度 | API 区分安装、在线、准备与占用，带最近观察信息 |
| N05 | 资源冲突 | 同一独占资源只有一个有效持有者，冲突明确返回 |
| N06 | 重启持久化 | 登记与撤销保持；在线/运行状态重新探测，不复活旧连接 |
| N07 | 停止/到期 | 不接受新执行，正确解除控制或清理自建资源 |
| H01 | 本机 HTTP | 正确的 DNS/代理/CA 环境、原始响应与输出位置 |
| H02 | 写请求后断线 | 不自动重放，报告技术状态/结果未知 |
| W01 | 原生连接 | 官方 SDK 建立受保护连接，版本匹配，节点本机启动浏览器 |
| W02 | API 参数 | 代表性 Locator、Context、Page 方法和额外参数不被静默丢弃 |
| W03 | 事件/文件 | 弹窗、下载、上传、二进制帧、输出位置与关闭行为保持合同 |
| W04 | 已有浏览器 | 复用正确原页面/登录状态，授权与停止有效 |
| W05 | 范围限制 | 不支持方法明确返回；不把局部扩展支持标成完整协议支持 |
| A01 | Android 准备 | 未授权/离线可识别，授权后选择正确设备 |
| A02 | 原生 Appium | capabilities/actions/已启用驱动扩展、原生错误没有错误转译或丢失 |
| A03 | 设备中断 | 拔线/锁定/观测不足状态明确，用户数据不被误清理 |
| G01 | 背压 | 大输出和慢接收者不会无限堆积，也不使停止消息长期失效 |
| G02 | 路由隔离 | 会话的数据/事件不会流向其他获授权连接 |
| S01 | 数据库负载 | 高频协议帧不落库，短数据库操作不阻塞网关事件循环 |

服务验收关注执行事实、原生语义和资源生命周期，不以某个外部业务的 PASS/FAIL 作为节点服务自身的返回字段。

## 4. 容量目标与性能验证

### 4.1 已确认的规划目标

| 指标 | 首期目标 | 条件与含义 |
| --- | --- | --- |
| 用户规模/在线客户端 | 100 用户，暂按 100 个在线客户端 | 每用户 1 个在线客户端、每节点一条控制连接；多数只发送心跳、能力更新与少量查询 |
| 活跃执行 | 10 个轻量并发会话 | 执行工具运行在节点机器，网关异步转发；不是持续录像或大截图吞吐承诺 |
| 服务端 | 单实例、单 ASGI Worker | 参考 Linux、2–4 vCPU、4–8 GB 内存；报告必须记录真实机器与网络规格 |
| 大输出 | 单独测量 | 记录截图、录像、文件和事件的大小、频率、峰值及带宽，不从轻量测试外推 |

用户已将首期规模确定为 100 用户、10 并发执行。容量估算假设每名用户只有 1 个在线客户端；同一用户有多个在线节点时按实际连接数累计，不能仅按用户数推算网关负载。用户规模是容量口径，不增加业务账户中心。10 并发指全服务的轻量活跃执行会话，不是每节点并发数，也不直接作为写死的配额。持久登记的节点总数、当前在线节点数与正在执行的会话数分别统计。这些是用户确认的规划目标，尚未证明上述参考规格一定达到目标。

按 WebSocket 原生执行隧道计算，网关连接量约为 `N + 2W`：`N` 是节点控制连接数，`W` 是活跃 WebSocket 执行会话数，每个会话有调用方入口和节点出站隧道。因此 100 个在线节点、10 个此类会话约为 120 个 WebSocket 连接；另计管理 HTTP、Appium HTTP 和本地转接等连接。不能把 100 个节点等同于服务器总共只有 100 个连接。

估算示例：若应用心跳为 30 秒一次，100 个节点平均约产生 3.3 次应用心跳/秒，另有协议保活开销；若 10 个会话每个产生 200 KB/s 载荷，单向穿过网关的数据就需要约 16 Mbps 入站与 16 Mbps 出站带宽，另加协议开销。这里 KB 按十进制计算；这些是假设数据，不是实测吞吐。

### 4.2 实现约束

- 网络转发、心跳和子进程等待采用异步方式；数据库、耗时资源探测和大文件处理不直接阻塞网络事件循环。[asyncio 阻塞行为](https://docs.python.org/3.14/library/asyncio-dev.html)
- 控制与执行通道分离；原生载荷按需转发，不在网关解码截图、生成录像或逐帧落库。
- 转发队列有界，慢接收者触发背压；消息大小和缓冲上限按原生后端能力验证，不静默截断载荷。[websockets 内存与缓冲](https://websockets.readthedocs.io/en/stable/topics/memory.html)
- 锁定 Uvicorn 的 WebSocket 实现并核对实际配置，不能将不同实现的队列参数视为完全等价；部署时检查文件描述符数量、代理长连接超时和网络限额。[Uvicorn 配置](https://uvicorn.dev/settings/)

### 4.3 压测与通过条件

先递增到 100 条控制连接，再在 100 个在线节点下加入 10 个轻量执行会话。预先固定并记录心跳频率、消息大小、每秒消息量和管理查询频率，避免只报告连接数。稳定负载至少持续一小时，并覆盖重复建立/释放会话。

记录管理请求延迟、事件循环延迟、连接数、并发原生流、转发带宽、缓冲队列和内存、重连与关闭耗时。用小/大观测、正常/慢接收者、稳定/断连分别测试。

通过条件：达到目标连接/会话数量；稳定网络下没有非预期断连；受测命令、响应和事件保持会话归属与顺序；队列与内存不因持续积压或重复关闭而无界增长；慢接收者不会使控制通道永久失效。延迟按 p50/p95/p99 记录，重流量、停止和集中重连各有独立结果，不预先将未知数值写成 SLA。

模拟节点和协议载荷用于测量网关容量；官方 SDK、真实客户端、浏览器和 Android 真机用于验证执行语义。两类结果分别记录，不能以模拟转发成功代替实际工具操作通过。

节点数量不是充分指标：少量录屏/截图流也可能比大量空闲节点更重。没有测量前不承诺容量上限、后台点击可靠性或固定恢复时长。若未达目标，先检查阻塞调用、消息量、缓冲和带宽，再评审调整方案；不直接增加 Worker 或 Redis。

数据库主要是低频控制元数据。若测试发现写入竞争先检查是否错误地将心跳/帧全部落库，不先假定必须换 Redis 或 PostgreSQL。

## 5. 何时扩展架构

| 观测到的需要 | 下一步评审 |
| --- | --- |
| 管理查询持续被转发负载影响 | 独立网关进程/服务及其路由合同 |
| 单实例连接/带宽成为实际瓶颈 | 多网关连接归属与定向转发 |
| 多主机共同写元数据、SQLite 写入冲突明显 | 客户端/服务器数据库 |
| 多实例需要即时共享归属/通知 | Redis 或消息系统，明确消息可靠性 |
| 客户要求无需 Python 环境安装 | 客户端打包/安装引导及运行时分发专项 |

每次扩展都先明确故障行为和验证标准。加入 Redis 本身不能解决连接持有、旧执行者停止或动作结果未知。

## 6. 定稿状态

**首期方案已确认，R0/R1 基础服务与控制面已实施并验证；R2–R6 尚未实施。** 采用 Python 3.14/Pydantic V2、同进程管理与网关、SQLite 与内存，不增加 Redis；容量采用本文件第 4 节的规划与压测目标。

后续依次按 R0–R6 落实并验证。依赖支持说明、方案确认与产品运行通过是不同证据；执行工具的原生运行时和版本兼容仍是必要条件，不能因本方案定稿省略验证。
