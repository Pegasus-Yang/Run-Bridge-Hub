# 安全机制与授权边界

[文档导航](../README.md) · [接口 Web 与 App 执行方案](接口Web与App执行方案.md)

本文件最初按平台统一管理节点的产品模式讨论授权。最新独立服务模式见[独立节点服务与对外契约](独立节点服务与对外契约.md)：节点所有者决定资源与底层能力范围，调用方平台决定其自身用户和 Agent 的使用策略，两个系统不必共享租户或项目模型。

## 1. 核心判断

**获得适当授权的测试节点是可行的软件形态。** 安全系统会限制无授权接管、默认 Profile 调试、设备调试、桌面录屏和特权操作，部分企业会直接禁用这些能力。应将限制变成可检测的准备条件和明确的支持范围。

用户对客户端的安装授权、平台账户对节点的使用权、浏览器对页面的授权、手机对调试主机的信任、客户对数据回传的许可，分别属于不同边界。任何一层成功都不能替代其余几层。

## 2. 会实际影响方案的机制

| 机制 | 已核实事实或影响 | 产品处理 |
| --- | --- | --- |
| Chrome 默认 Profile 保护 | 136+ 限制传统调试端口/pipe 对默认数据目录的使用 | 独立测试 Profile；现有浏览器使用正式授权入口 |
| 扩展 debugger 权限 | 需声明权限，CDP 域受限 | 显示范围、处理拒绝/撤销；逐项测能力 |
| Chrome 企业策略 | 当前官方 debugger 文档说明，受禁止主机、截图或 DLP 策略约束时 attach 可以失败 | 展示策略原因；由客户管理员决定是否准入 |
| Chrome 原生确认 | 有明确启用/确认流程，Profile 访问范围较宽 | 提示有效范围，不包装成单标签页细粒度授权 |
| macOS Gatekeeper | 默认分发路径检查开发者身份、公证与完整性 | 签名与公证，发布可校验安装包 |
| macOS Accessibility/屏幕录制 | OS 桌面控制和录屏要相应权限 | 按实际功能申请，提供权限探测和引导 |
| Windows UAC | 提权默认使用 secure desktop 和确认/凭据提示 | 安装或必要配置时处理；正常执行尽量不提权 |
| Android ADB | USB 调试和 RSA 主机确认 | 注册设备时检查 authorized/online，等待用户确认 |
| iOS 真机 | 设备信任、Developer Mode、WDA 签名等条件 | 提供单独准备流程和兼容探测 |
| App 保护内容 | Android FLAG_SECURE 等可能阻断截图 | 不把截图缺失解释为业务正常，明确能力不足 |
| 企业网络/数据政策 | 节点出站、观测回传、第三方模型可能受限制 | 先确认网络和数据路径；需要时选择私有部署 |

浏览器事实分别来自 [Chrome 调试端口](https://developer.chrome.com/blog/remote-debugging-port)、[debugger API 及企业限制](https://developer.chrome.com/docs/extensions/reference/api/debugger)、[Chrome 原生确认](https://developer.chrome.com/blog/chrome-devtools-mcp-debug-your-browser-session)。系统事实来自 [Apple Gatekeeper](https://support.apple.com/en-ca/guide/security/sec5599b66df/web)、[Accessibility](https://support.apple.com/guide/mac-help/allow-accessibility-apps-to-access-your-mac-mh43185/mac)、[录屏权限](https://support.apple.com/en-gb/guide/mac-help/mchl592e5686/mac)、[Windows UAC](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/user-account-control/how-it-works)。设备细节及来源见场景执行文档。

浏览器协议内的 DOM 操作、页面截图与整个操作系统的鼠标控制、桌面录制不同。仅做 Playwright/WebDriver 操作通常不需要因此申请完整桌面控制权限；具体浏览器或系统弹窗仍以实际版本为准。不要为三类测试一开始要求全磁盘、全桌面和长期管理员权限。

## 3. 客户端和扩展的关系

浏览器扩展适合操作现有页面；跨平台原生客户端适合管理节点身份、网络连接、API 请求、驱动进程、文件和 USB 设备。仅靠浏览器扩展不能覆盖本需求的全部执行职责。

推荐完整产品使用原生客户端加可选浏览器扩展。扩展与客户端可以通过 Native Messaging 连接，绑定允许的扩展 ID；官方 `allowed_origins` 不支持通配符。[Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)

首轮可先用官方扩展加本地工具子进程验证，不必立即替换官方桥接或制作完整桌面 UI。若使用本地 HTTP/WebSocket 服务，应仅绑定回环地址，校验连接身份和来源，避免任意网页访问本机执行接口。MCP Streamable HTTP 规范要求校验 Origin，并建议本地服务绑定 localhost 和使用认证。[MCP 本地传输保护](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

Native Messaging 和 localhost 都不是“天然可信”：仍需要验证消息结构、调用者、资源范围及用户授权。客户端不接受来自页面内容的节点绑定、上传地址或任意执行命令。

## 4. 最小产品必须具备的控制

以下是完成远程测试所需的范围控制，不是额外建设通用远控平台。

| 控制 | 必要原因 | 首期实现建议 |
| --- | --- | --- |
| 租户与项目绑定 | SaaS 同时处理多个客户 | 从认证身份派生；每个资源/结果检查归属 |
| 出站认证连接 | 不要求客户暴露执行端口 | TLS、短期会话凭据、节点撤销；mTLS 可按企业需要增加 |
| 资源授权 | 用户只同意操作指定系统/设备 | 指定浏览器会话、设备、测试服务、授权文件 |
| 工具限制 | 避免测试接口变成任意代码执行 | 固定工具集合和参数验证；拦截未授权工具 |
| 本机停止入口 | 用户要能结束远程控制 | 停止接收新动作、解除控制、清理自建资源 |
| 凭据与文件限制 | 测试需要秘密/附件，不需要整个电脑 | 本地凭据引用、单独文件授权、不导出密码库 |
| 证据和审计 | 调查超时、错误动作和未知结果 | 保存动作、授权、节点、观测及清理状态 |
| 受控更新 | 客户端常驻且能操作测试资源 | 验证签名/完整性，使用固定发布版本 |

当前读取的 Playwright MCP 版本包含 `browser_evaluate` 和 `browser_run_code_unsafe`，后者可在 Playwright 服务进程执行任意 JavaScript。面向 Agent 的受限工具封装可以过滤这些能力；独立节点服务则按所有者授予的资源和权限暴露原生能力，并明确其范围。页面内 JavaScript 与宿主进程代码执行应分别说明，不能为方便 Agent 而静默删掉底层参数，再宣称完整 API 支持。

官方 Playwright MCP 明确表示它不是安全边界；`--allowed-origins` 等配置也不是隔离边界，且不影响重定向。因此不能根据一个域名白名单就宣称客户 Profile 完全隔离。[固定提交的 MCP 配置及安全说明](https://github.com/microsoft/playwright-mcp/blob/b8b4183e099f136cbec0388a6088d4aa2f6b9685/README.md)

对于原生 CDP/Playwright 协议转接，调用者获得的能力较宽，很难等价实施细粒度动作限制。建议仅给专用受管理浏览器使用，辅以独立 Profile 和网络/进程隔离；日常浏览器优先使用可审计的工具接口。页面子资源、跨源 iframe、重定向和 Service Worker 的行为也要进入实测范围。

Appium 官方建议运行在本地或受保护网络，不向公网暴露服务端口；不安全扩展能力默认关闭。产品默认不启用 `--relaxed-security`，需要的能力按场景单独允许。[Appium Server Security](https://appium.io/docs/en/latest/guides/security/)

## 5. Agent 输入不是授权来源

页面文字、截图、接口响应和 App 内容都是被测数据，可能包含“上传本地文件”“访问另一个系统”等指令。模型将其理解为操作建议时，节点仍按用户和项目已确定的授权判断，不接受页面自称的许可。

建议让授权由平台确定性策略和节点本地策略共同执行。Agent 只请求工具，不能自行扩展测试域名、设备、文件目录或上传目标。用户确认新的资源范围后，再更新授权。

企业节点可以配置专用测试账号、测试 Profile 和经过批准的目标服务。一个授权域名并不意味着“域名中的所有破坏性业务操作都已允许”；测试数据和业务写入范围还应由项目约定限定。

## 6. 信息保护的真实边界

| 内容 | 能否留在客户环境 | 对云端 Agent 的影响 |
| --- | --- | --- |
| API token、Cookie 原值、证书私钥、Apple 签名资产 | 建议默认留在节点，以句柄引用 | Agent 可请求认证动作，无需读取原值 |
| 页面 DOM/UI 树、接口正文 | 可筛选或脱敏 | 删掉关键业务信息可能导致无法分析 |
| 页面/手机截图 | 可裁剪、遮挡或禁止 | 纯视觉 Agent 可能失去必要观察能力 |
| 录屏、下载附件和日志 | 可本地保存，仅按需求上传 | 云端报告证据范围会减少 |
| Agent 源代码、系统提示词、模型服务凭据 | 可留在平台 | 客户仍能观察动作序列和对外效果 |

秘密留在节点不等于不存在间接泄漏：响应、地址栏、DOM、控制台、截图和日志仍可能包含秘密。回传前应按数据类型处理；截图脱敏不能只靠文本正则。无法可靠处理的敏感画面应按约定不上传，或限定在专用测试环境。

没有观测数据回传的纯云端 Agent 不能理解任意内网业务页面。可以只做本地确定性校验，或者提供客户私有环境中的 Agent；这两种产品能力和成本需要单独评审。

## 7. 无人值守与人工授权

建议产品区分：

- 交互模式：复用用户当前会话，遇到浏览器连接、MFA、设备权限和状态变化时等待用户。
- 专用节点模式：客户预先授权测试浏览器/设备与目标服务，维持在线，按许可范围自动运行。

无人值守不是“能够自动通过一切系统提示”。系统更新、证书失效、设备信任变化或企业策略调整仍可能要求重新准备。状态应显示“需要用户操作”或“受策略限制”，而不是统一展示测试失败。

## 8. 技术上的明确阻断条件

节点不能出站连接平台；客户禁止将所有必要观测传出；企业策略禁用所需 debugger/截图；手机无法取得调试授权或运行所需 WDA；被测内容只存在于无法观察的受保护界面。以上条件可能使对应模式不可实施。

这不否定整个平台架构：应记录阻断的是哪个节点、场景或数据路径，并提供客户认可的替代部署方式。不能承诺签名安装包或更换传输协议就能解决所有策略限制。
