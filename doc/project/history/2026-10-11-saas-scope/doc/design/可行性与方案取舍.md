# 可行性与方案取舍

[文档导航](../README.md) · [研究首页](../../README.md)

## 1. 结论及适用前提

**可以实施，建议先验证再进入产品开发。** 将 AI 决策与设备执行拆开，没有违背浏览器、HTTP 或移动自动化的基本工作方式。真正决定落地效果的是客户授权、观察数据能否回传、执行环境是否稳定，以及远程会话能否正确管理。

本报告采用以下假设：客户自愿安装或启用执行端；只操作客户指定的测试资源；节点允许主动连接平台；客户允许必要且经过约定处理的观测进入平台。如果任一条件不成立，需要更换部署方式或缩小支持范围。

自然语言用例仍可作为业务输入。节点能力、浏览器句柄和驱动参数应由客户端探测、平台匹配，不需要客户先手写定位器和完整断言字段才能开始使用。

## 2. 对四项构思的判断

### 2.1 平台作为管理和调度中心

这是常规 SaaS 控制面的职责：账户与组织、项目、用例版本、运行记录、节点目录、访问权限和报告。需区分“平台用户”“组织/租户”“项目”“节点所有者”和“允许使用节点的人”。一台已注册电脑不应自动向组织内所有账户开放。

建议运行时固定用例版本、Agent/工具版本、节点能力快照和授权范围。用户随后修改用例，不能改变已经运行到一半的任务。

### 2.2 Agent 在平台，设备执行在客户环境

可以实施。Agent 根据用例和观测选择下一步；执行端把明确的操作变成实际 HTTP 请求、浏览器动作或设备操作。

执行端并非零逻辑：仍包含驱动进程、元素等待、动作超时、截图/UI 树采集、文件处理和会话清理。这些确定性的工具行为不要求把模型密钥、系统提示词和 Agent 决策循环交付给客户。

建议把“大脑留在平台”定义为 **模型调用、任务规划、用例理解和报告推理留在平台**，而非“客户电脑只能执行一个没有状态的点击函数”。后者会让每次等待和观测都产生额外网络往返，降低可靠性。

### 2.3 命令转发到本机执行

可以实施。完整链路应是：

> 平台 Agent → 云端工具网关 → 已建立的节点连接 → 本地执行器 → 被测系统 → 观测与结果 → 平台 Agent。

不要要求平台直接连接客户电脑的公网 IP。建议客户端主动连接平台，平台利用已建立的双向通道发送命令。自托管 Runner 的出站接入有成熟参考；GitHub 官方要求 Runner 能通过 HTTPS 443 出站获取任务。[GitHub Runner 通信要求](https://docs.github.com/en/actions/reference/runners/self-hosted-runners)

“注册成功”“命令送达”“驱动执行完成”“业务断言通过”是四种不同事实。需要分别记录，不能根据客户端返回成功就认定用例通过。

### 2.4 注册时探测环境，复用已登录浏览器

可以实现能力发现和授权复用，但应拆成两步：

1. 注册时发现支持的浏览器、扩展、移动驱动及用户愿意登记的设备。
2. 每次运行前检查当前连接、权限、资源占用和业务登录状态；可复用才跳过启动或登录步骤。

浏览器存在不代表调试通道存在；Cookie 存在不代表登录仍有效；节点在线不代表手机已授权；此前授权过不代表当前所有新标签页都可控制。登录状态最好用用户指定系统的可观察业务信号确认，并允许人工处理 MFA。

## 3. 三种架构不要混淆

| 路线 | AI/流程位置 | 浏览器或手机位置 | 内网访问方式 | 对当前需求的适合程度 |
| --- | --- | --- | --- | --- |
| A：云端 Agent + 本地执行 | 云端 | 客户电脑或客户手机 | 本地执行器直接访问 | **首选**，符合浏览器登录和自有手机复用 |
| B：云端 Agent + 云端浏览器/设备 | 云端 | 平台或第三方设备云 | 客户安装网络隧道 | 适合统一云端环境；不能直接复用客户本机浏览器/USB 手机 |
| C：私有 Agent + 本地执行 | 客户私有环境 | 客户环境 | 内部网络 | 适合数据不能出网的企业；和纯 SaaS Agent 的部署目标有取舍 |

BrowserStack Local 官方说明的浏览器/设备位于 BrowserStack 云端，本地组件转发网络请求。它证明出站隧道是成熟方案，但不证明产品已经实现了路线 A。[BrowserStack Local 架构](https://www.browserstack.com/docs/local-testing/how-local-testing-works)

三条路线都可以具有“平台统一管理”的外观，不能仅凭有桌面客户端或内网连接器就判断执行架构相同。

## 4. 客户端通信有三种实现策略

| 策略 | 优点 | 代价 | 建议 |
| --- | --- | --- | --- |
| 工具 RPC/MCP：云端发 `click`、`snapshot`、`http.request` 等，本地驱动执行 | 接口稳定、动作等待在本机、较容易约束能力 | 要适配工具与观测；现有 Agent SDK 未必直接支持 | **作为产品默认路线** |
| 标准协议转接：云端 Playwright/WebDriver/Appium 客户端连接受保护的本地服务 | 对依赖原生 SDK 的 Agent 改动较小 | 协议往返较多、版本耦合、能力范围更宽 | 作为确有 SDK 需求的适配路线 |
| 完整自研浏览器 CDP Relay：把扩展 debugger API 映射成 CDP 服务 | 可深度定制日常浏览器接入 | 需要目标、事件、iframe/worker、浏览器级命令等兼容 | 原型后再决定，避免首轮全量自研 |

MCP 可以作为云端 Agent 的工具接口，但不是节点调度系统。建议对 Agent 暴露云端 MCP/工具服务，节点传输另用认证出站连接；不假定任意 MCP 客户端都原生支持自定义 WSS。[MCP 传输规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

如果使用 browser-use 等必须持有 CDP 浏览器连接的 SDK，则工具 RPC 不能被当作透明替代物。应实现适配层，或为该运行器提供单独的受保护协议连接。这是选型影响实现范围的重要区别。

## 5. 安全机制会不会把它判成恶意控制

自动化和远程控制本身有合法产品与官方 API 支持。行为相似并不会使方案在技术上普遍不可行；**软件签名、用户授权和企业策略是否允许，才是实际准入条件。** 已核实的限制与例外见[安全机制与授权边界](安全机制与授权边界.md)。

需要避免把“注册一次”解释为“今后所有系统权限、浏览器页面和设备都永久允许”。可以提供用户预授权的专用测试资源和无人值守模式，但浏览器/操作系统要求的确认仍要尊重。

签名、公证和明确产品说明能帮助分发和企业审查，不能保证所有终端防护软件必然放行。企业禁用调试、禁止截图或禁止观测数据出网时，应明确返回受策略限制，而不是反复尝试规避。

## 6. 不能同时保证的目标

| 同时提出的要求 | 冲突原因 | 可以选择的方向 |
| --- | --- | --- |
| 云端 Agent 理解私有页面，但页面信息完全不离开客户环境 | 模型缺少分析所需观测 | 允许有限观测；本地确定性校验；或私有化 Agent |
| 无需用户授权，直接控制任意日常浏览器和手机 | 浏览器、设备调试和系统权限有授权边界 | 用户显式选择资源；提供已预配置的专用测试机 |
| 复用同一日常浏览器账号，同时提供完整租户/账号隔离 | 同一 Profile 的 Cookie、存储和登录状态共享 | 同一会话独占；不同账号用独立 Profile/测试环境 |
| 支持日常电脑长期无人值守，同时允许随时休眠、断网、拔设备 | 运行条件无法保证 | 等待人工恢复；或使用常在线专用节点 |
| Agent 内部实现不发给客户，且客户完全看不到测试策略 | 客户可以观察动作和输入输出 | 保留源代码/提示词/模型密钥；接受操作行为可见 |

## 7. 建议的评审结论

**可以进入最小原型验证。** 先确认真实客户网络和观测回传政策，再用成熟执行工具验证“一台节点、一个已登录页面、一个内网 API、一个 Android 设备”的闭环。iOS、跨浏览器、完全后台和多节点并发应分别增加验证，不沿用第一个 Web 演示的通过结论。
