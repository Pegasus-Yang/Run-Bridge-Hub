# RunBridge Hub 部署与运行

[文档导航](../README.md) · [Hub 配置与凭据](../reference/部署配置与凭据.md) · [运行与排障](运行与排障.md)

适用于 **runbridge-hub 0.5.1**。本指南在独立的 Hub 服务端机器安装发布包，完成监听、登记凭据、MCP、网络接入及维护。Node 在使用者的另一台设备上部署，由 Node 所有者按 RunBridge Node 项目文档操作。

下文 `192.168.50.10` 表示示例 Hub 服务器地址，部署时替换为实际地址。Hub 内部健康检查使用自身回环地址；交给远程设备的地址应为实际可达 IP／域名。

## 1. 部署前准备

| 项目 | 要求 |
| --- | --- |
| Python | 标准 CPython 3.14.x，项目范围为 >=3.14,<3.15；可由 uv 准备 |
| uv | 设备已安装的全局 uv；交互终端、SSH 或进程管理器均须能找到它 |
| 安装包 | 发布者交付的 `runbridge_hub-0.5.1-py3-none-any.whl`；本指南不假定已发布到公共 PyPI |
| 文件系统 | 独立部署目录、可写的 SQLite 和私有凭据目录 |
| 网络 | Node 和调用方可以访问 Hub 的 HTTP(S)／WebSocket 入口 |
| MCP，可选 | 需要 Agent 工具时选择 `mcp` extra；浏览器由远程 Node 提供 |

Hub 基础安装无需浏览器、Node.js、npm 或 Browscreen。MCP extra 包含 SDK，Hub 仍无需安装本机 Chromium。系统与网络条件在目标机器验证；当前公开实测以 macOS ARM64 和 Ubuntu ARM64 相关组合为主。

源码安装、构建和同机联调见[开发与联调](../development/本地开发与联调.md)。

## 2. 安装 Hub 发布包

在 **Hub 服务器**创建部署目录，将交付的 wheel 放入该目录：

```bash
mkdir -p ~/runbridge-hub
cd ~/runbridge-hub
uv --version
uv venv --python 3.14 .venv
```

已有 `.venv` 时复用它，首次安装才执行创建命令。按实际场景选择下面一种安装目标。

仅提供 HTTP、原生浏览器协议和画面转发：

```bash
uv pip install --python .venv/bin/python ./runbridge_hub-0.5.1-py3-none-any.whl -i http://mirrors.aliyun.com/pypi/simple/ --trusted-host mirrors.aliyun.com
```

还需要 MCP 浏览器工具：

```bash
uv pip install --python .venv/bin/python './runbridge_hub-0.5.1-py3-none-any.whl[mcp]' -i http://mirrors.aliyun.com/pypi/simple/ --trusted-host mirrors.aliyun.com
```

验证安装：

```bash
.venv/bin/runbridge-hub --help
uv pip check --python .venv/bin/python
```

每条命令的 `--python` 选中当前 Hub 的环境；`uv pip` 不要求环境内存在 `pip`。如发布者同时交付本版本的 `deploy-constraints.txt`，在安装命令中增加 `--constraint ./deploy-constraints.txt`。这是 UTF-8 requirements 格式的依赖约束，由发布者随包提供；单独固定 wheel 不会固定所有依赖版本。

后续命令固定在此部署目录执行。也可以使用全局 uv 调用相同环境，例如 `uv run --no-project --python .venv/bin/python runbridge-hub --help`；发布包部署不使用源码项目的锁文件参数。

## 3. 准备 Hub 文件

```bash
umask 077
mkdir -p .runbridge
chmod 700 .runbridge
.venv/bin/runbridge-hub generate-token --output .runbridge/enrollment.token
```

已有登记文件时跳过生成命令，命令拒绝覆盖。首次生成文件为一行随机令牌原文，不是 JSON；不加引号、`Bearer ` 或 `token=`。

| 文件 | 格式／生成者 | 用途 |
| --- | --- | --- |
| `.runbridge/enrollment.token` | Hub 命令生成的 UTF-8 纯文本，POSIX 权限 0600 | Hub 启动验证新节点登记；将同一份文件安全交给 Node 所有者 |
| `.runbridge/hub.sqlite3` | Hub 启动自动创建的 SQLite 数据库 | 持久保存节点、访问许可、会话和请求元数据 |
| `deploy-constraints.txt`，可选 | 发布者导出的 requirements 约束文件 | 复现依赖，不是 Hub 启动配置 |

Hub 使用命令行参数和登记环境变量读取配置。字段格式、优先级和全部参数见[Hub 配置与凭据](../reference/部署配置与凭据.md)。

## 4. 启动并开放远程连接

在 Hub 服务器前台启动：

```bash
.venv/bin/runbridge-hub serve --host 0.0.0.0 --port 8787 --db-path .runbridge/hub.sqlite3 --enrollment-token-file .runbridge/enrollment.token
```

`0.0.0.0` 是监听所有网卡的地址；远程客户端使用服务器实际地址，如 `http://192.168.50.10:8787`。也可将 `--host` 指定为选定网卡地址。防火墙应允许目标网络访问该端口。

保留服务终端，在 Hub 本机检查：

```bash
curl --fail http://127.0.0.1:8787/health
```

预期为 `{"status":"ok","protocol_version":1}`。再由远程使用者检查同一服务的实际访问地址。只有远程健康检查也通过，才交付登记入口；本机健康不证明远程路由可用。

长期运行由部署者的进程管理器管理：工作目录固定为部署目录，解释器和 CLI 使用该目录的绝对路径，保留日志，使用 SIGTERM／正常停止流程。Hub CLI 固定一个 ASGI Worker；SQLite 以外的活动连接和预约属于当前进程，不能直接增加 Worker 或并排启动多个实例共享路由。

## 5. 可选：启用 MCP

先按第 2 节安装带 `[mcp]` 的包，再将基础启动命令替换为：

```bash
.venv/bin/runbridge-hub serve --host 0.0.0.0 --port 8787 --db-path .runbridge/hub.sqlite3 --enrollment-token-file .runbridge/enrollment.token --enable-mcp --mcp-native-url http://127.0.0.1:8787 --mcp-allowed-host 192.168.50.10:8787
```

这里的额外 Host 必须改成请求实际到达 Hub 时的 Host。通过 HTTPS 域名代理访问时，使用该域名，例如 `--mcp-allowed-host hub.example.com`。`--mcp-native-url` 是 Hub 进程内部连接自身原生路由的根地址，通常仍为回环地址。

| 设置 | 含义 |
| --- | --- |
| `--enable-mcp` | 安装依赖后仍须显式开启 `/mcp` |
| `--mcp-native-url` | 当前 Hub 内部可达的 HTTP(S) 根地址，不含 `/mcp` 或其他路径前缀 |
| `--mcp-allowed-host` | 可重复，追加允许的 Host，不带协议或页面路径 |
| `--mcp-allowed-origin` | 可重复，允许网页 Origin；无 Origin 的服务端客户端无需设置 |

允许列表不使用全局 `*`。所有 MCP 请求仍需有效访问许可；登记文件不能作为 MCP 凭据。Agent 配置和工具调用见[MCP 浏览器接入](../user-guide/MCP浏览器接入.md)。

## 6. 交付给 Node 所有者的资料

| 资料 | 要说明的内容 |
| --- | --- |
| Hub 基址 | 从 Node 及调用方网络实际可达的 HTTP(S) 地址；例如局域网的 `http://192.168.50.10:8787` |
| 登记文件 | 第 3 节生成的同一份 `enrollment.token`；通过可信文件传输交付 |
| 服务能力 | 是否启用 MCP、可用的代理／TLS 入口和维护安排 |

Node 所有者负责其设备上的身份登记、浏览器准备和访问许可签发。Hub 部署者无需在本服务器安装或启动 Node。调用方取得的是所有者签发的访问 JSON，按[Hub 接入检查](../user-guide/快速开始.md)验证。

## 7. 网络、代理与 TLS

Node 主动连接本服务，Hub 接收 HTTP 和 WebSocket。浏览器的 CDP 地址保留在 Node 设备本机；它不属于 Hub 的监听配置。

- 生产入口提供可信 HTTPS／WSS。Hub CLI 无证书参数，TLS 终止由部署设施提供。
- 反向代理转发 Authorization、User-Agent、`x-playwright-*` 以及 WebSocket Upgrade；连接超时须覆盖心跳和会话租期。
- 路径前缀由代理一致映射到 Hub 原路由。MCP 的内部原生地址仍是无前缀根地址，允许列表匹配代理实际转发的 Host／Origin。
- MCP 默认只允许回环 Host；使用外部地址时配置对应允许项。Hub 没有通用 HTTP CORS 配置，网页集成应由调用方平台处理同源代理或跨域设计。

这些要求不等同于目标生产代理已经验证，部署后仍需在实际链路完成远程查询和连接检查。

## 8. 停止、备份与升级

先通知使用者结束活动会话，再正常停止 Hub。停止或重启会中断旧会话；Node 重连后重新上报状态，调用方申请新会话，旧 SDK 对象不会恢复。

备份持久数据时正常停止 Hub 后复制数据库，或使用 SQLite 一致性备份。活跃 WAL 模式下不能只随意复制主数据库文件。保留登记文件和数据库的对应部署关系。

Hub 0.5.1 使用 SQLite schema 3，启动自动迁移 v1／v2；回退使用升级前的一致性备份。升级在原部署环境安装新 Hub wheel，再使用原数据目录和配置启动；MCP 部署继续安装对应 extra。升级后核对健康、远程节点上报、访问授权和清理状态，不能将健康响应当作浏览器业务成功。
