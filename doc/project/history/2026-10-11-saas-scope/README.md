# SaaS AI 测试平台与用户执行节点可行性研究

研究日期：2026-10-11（Asia/Shanghai）。范围：接口测试、Web 自动化、Android/iOS App 自动化；本次交付为研究与设计，不包含平台或客户端代码实施。

## 核心结论

**方案可行，适合采用“应用平台与 AI 决策 + 独立节点控制服务”的架构。** 平台与 Agent 构成应用系统；节点注册、连接网关、客户端及执行器构成独立节点系统。两者通过访问凭据、能力查询及公开执行协议对接；被测系统的网络连接和设备交互发生在用户环境中。

当前推荐的独立边界、原生 API 保留方式和最小运行合同见[独立节点服务与对外契约](doc/design/独立节点服务与对外契约.md)。平台不需要参与节点内部注册，也不需要让节点理解用例、Agent 或平台租户模型。

| 用户构思 | 判断 | 必要边界 |
| --- | --- | --- |
| 平台集中保存账户、用例和用户数据 | 可以实施 | 采用租户隔离、项目权限和独立的节点授权 |
| Agent 留在平台，客户电脑负责执行 | 可以实施 | 客户端仍要运行自动化驱动、动作等待和观测采集；不需要承载 AI 规划 |
| 启动浏览器、点击、输入等命令发往本机 | 可以实施 | 需要出站连接、资源独占、命令关联和断线处理，不能只做消息转发 |
| 注册时了解节点，复用已登录浏览器 | 有条件可实施 | 注册只能获得能力快照；执行前必须重新确认浏览器可连接、授权仍有效和业务登录状态 |
| Agent 实现不交付给用户 | 可以保留服务端实现 | 用户仍能观察本机操作、工具请求和测试效果，不能保证算法行为完全不可推断 |

这里的安全机制通常表现为安装、浏览器连接、设备调试、数据回传的授权门槛，不会普遍禁止这种产品形态。但在企业禁用调试或截图、节点不能访问平台、客户不允许必要观测数据出网的环境下，这种纯云端 Agent 模式可能无法使用。

## 推荐方向

1. 平台保存用例、编排运行、调用模型和形成报告；自行选择原生 SDK 或面向 Agent 的工具封装。
2. 节点服务自行管理注册、网关、访问凭据和资源会话；客户端主动连接节点网关，执行工具保留在客户环境。
3. Web 提供两个明确模式：平台管理的独立测试浏览器，以及用户授权复用的现有浏览器。两者分别验证。
4. 首轮原型同时验证内网 API 和已登录 Chrome 的复用闭环，再扩展 Android；iOS 单独验证环境准备和签名路径。
5. 分别开发应用系统与节点系统，通过稳定公开契约接入；执行面尽量复用 Playwright/Appium 原生协议和参数，Agent 二次封装留给调用方。

产品主线建议直接使用执行 SDK，Playwright MCP、Midscene 等完整工具属于可选适配与原型参考。NATS、Temporal、frp 能承担不同基础职责，但不自动提供本产品的节点、授权和会话合同，详见[自研边界与中间件选择](doc/design/自研边界与中间件选择.md)。

最接近浏览器复用需求的公开方案包括官方 Playwright MCP 扩展、Chrome DevTools MCP 和 Midscene Bridge。Selenium Grid、自托管 Runner、mabl 和 Leapwork 提供了调度或本地执行的参考。BrowserStack Local、Sauce Connect 主要解决云端执行环境访问内网的网络问题，和本方案的执行位置不同。具体来源、许可证和适配边界见选型文档。

## 必须先判断的三个产品条件

- **网络条件**：客户节点能否主动连接平台，企业代理是否允许所选通信方式？客户被测系统不出公网，与节点能够出站连接平台可以同时成立。
- **数据条件**：允许哪些 DOM、截图、UI 树、接口响应进入平台及模型服务？系统位于内网，不意味着云端分析时数据仍全部留在内网。
- **运行条件**：产品面对用户日常电脑，还是专用测试机？前者适合人工登录和授权复用，后者更适合无人值守和并发回归。

这些是下一轮设计评审需要选择的条件，本报告不将其当作已经确认的客户需求。
