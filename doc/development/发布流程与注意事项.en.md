# GitHub Release and PyPI publishing workflow

[简体中文](发布流程与注意事项.md) · English

This guide records the workflow used for RunBridge Hub and Node and explains how other Python projects can adopt it. Read this overview before the project commands in [GitHub Actions and Releases](GitHubActions与Release.en.md) and [PyPI release preparation](PyPI发布准备.en.md). This document does not authorize a future push or upload.

## 1. Separate the three deliveries

| Operation | Trigger and permission | Delivery and acceptance |
| --- | --- | --- |
| Normal CI | Branch push / PR, `contents: read` | Tests, builds, installed-wheel checks, and an Actions artifact |
| GitHub Release | A `v*` tag or an existing tag supplied manually from main; publisher has `contents: write` | Build the tagged source; publish a draft only after downloading its assets and verifying digests |
| PyPI | Separately authorized upload using a PyPI token | Official JSON / simple index lists the files; downloaded digests and a fresh installation pass |

The current Actions configuration does not upload to PyPI or need its token. `GITHUB_TOKEN` is not a PyPI credential. Adopting Trusted Publishing later requires a separate PyPI trust relationship and GitHub OIDC permissions.

Project identifiers and existing release examples:

| Project | Repository | Distribution / example version | Extras |
| --- | --- | --- | --- |
| Hub | `Pegasus-Yang/Run-Bridge-Hub` | `runbridge-hub` / `0.9.3` | `mcp` |
| Node | `Pegasus-Yang/Run-Bridge-Node` | `runbridge-node` / `0.8.2` | `playwright,visual` |

Both example versions are already published. Do not recreate their tags or overwrite their files. Other projects must supply their actual package name, Python range, CLI, extras, tests, and runtime resources.

## 2. Prepare English PyPI metadata first

PyPI displays the description embedded in the distribution metadata; it does not follow changes to GitHub README or repository About settings. Configure the existing `[project]` table in `pyproject.toml`:

```toml
[project]
readme = { file = "README.en.md", content-type = "text/markdown" }
```

Use an English short `description` and make the default `Documentation` URL point to English documentation. Retain the Chinese README, Chinese documentation entry, and language switches. Licensing, authors, Python support, and project URLs must reflect the project.

Use public absolute URLs for README navigation and images. A GitHub file-page image URL may use `blob/main/...?...` with `raw=true`. Use static SVGs or images for architecture diagrams instead of relying on PyPI to execute Mermaid. Check public responses, media types, and content rather than only local file existence.

Inspect the wheel's `*.dist-info/METADATA` and sdist's `PKG-INFO`: `Description-Content-Type` must be `text/markdown`, and the body must match `README.en.md` at the build commit. Read the body with `get_payload(decode=True).decode('utf-8')` so Chinese language-navigation text is decoded correctly. PyPI may normalize quotation marks in dependency markers; compare their meaning using `packaging.requirements.Requirement`.

An uploaded filename cannot be overwritten or reused after deletion. To correct a published Chinese description, this workflow publishes a new version containing the English metadata. Do not move an old tag, rename an old package, or attempt replacement uploads. [PyPI troubleshooting](https://docs.pypi.org/publishing/troubleshooting/)

## 3. Validate a new version locally

1. Synchronize `pyproject.toml`, package `__version__`, `uv.lock`, current Chinese/English documentation, and changes. Build from a clean commit and preserve old versions and tags.
2. Run appropriate tests with the repository root `.venv`, then build both distributions. RunBridge selects `pytest tests -q -m 'not browser'`; other projects must choose tests according to their own contract.
3. Strictly check metadata and the long description. Define wheel/runtime resources and sdist contents; exclude `local/`, credentials, logs, caches, and raw historical evidence.
4. Create a fresh `.venv` outside the source checkout. Check base and extra installs, versions, site-packages origin, CLI help, configuration, and resources. Installation acceptance does not establish live service or browser acceptance.

Build from the appropriate repository root:

```bash
uv build --out-dir dist --no-sources -i http://mirrors.aliyun.com/pypi/simple/ --trusted-host mirrors.aliyun.com
```

By default, `uv build` builds the sdist and then a wheel from it; `--no-sources` checks independence from local source overrides. Follow the [PyPI guide](PyPI发布准备.en.md) to run strict Twine checks on the two exact files, explicitly providing `readme-renderer[md]`. Do not upload `dist/*`, which may include older versions.

Preserve existing local release files. To recheck an already published version, use a separate tag checkout and a new output directory. Record the source commit, workflow commit, and file digests separately.

## 4. Publish a GitHub Release through Actions

The new release commit should include `ci.yml`, reusable `validate.yml`, and `release.yml`. After validating, committing, and pushing the source, push its annotated `v*` tag. Branch pushes and PRs validate only.

The workflow checks tag, metadata, source, and lockfile before testing, building, and installing the actual wheel. The publisher consumes the same validation artifact without rebuilding. External Actions are pinned to commit SHAs; this project uses Node.js 24 versions of the artifact upload/download Actions.

When an existing tag predates the workflow, run the new workflow from **main** and supply the original tag. It checks out that tag separately. The default branch must contain `workflow_dispatch`, and the operator needs write access. [GitHub manual-run documentation](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)

```bash
gh workflow run release.yml --repo Pegasus-Yang/Run-Bridge-Hub --ref main -f tag=v0.9.3
gh workflow run release.yml --repo Pegasus-Yang/Run-Bridge-Node --ref main -f tag=v0.8.2
```

These are historical backfill examples. The releases already exist, so another run stops by design. Without `gh`, use Actions → Release → Run workflow on main with the tag input; creating another GitHub credential is unnecessary.

Uploaded assets are the wheel, sdist, `SHA256SUMS`, and `release-manifest.json`. GitHub's generated Source code zip / tar.gz links are different from the built Python sdist. Actions artifacts are currently retained for 14 days; use Release assets for durable downloads.

Confirm validation and publishing succeed and the draft becomes public, then download and check assets. The manifest's `source_commit` must match the tag; its `workflow_commit` may be a newer main commit during backfill. Inspect an existing release or draft before retrying; do not overwrite it automatically.

## 5. Publish the same Release files to PyPI separately

If a GitHub Release exists, reuse its wheel and sdist. Do not rebuild the same version from main after its README has changed. This Hub 0.9.3 example only downloads and checks existing assets:

```bash
rb_release_dir=$(mktemp -d)
gh release download v0.9.3 --repo Pegasus-Yang/Run-Bridge-Hub --dir "$rb_release_dir"
(cd "$rb_release_dir" && shasum -a 256 -c SHA256SUMS)
```

For Node, replace the repository and tag. Inspect the manifest source and embedded English description, then strictly check and install the downloaded distributions. Point upload commands at the exact files in this directory. Existing local `dist/` files may be used if they match the verified Release bytes.

Check `https://pypi.org/pypi/<distribution>/<version>/json` before uploading. An absent version can be published initially. For an existing version, compare filenames and digests instead of assuming matching names mean matching content.

Use the dry run and authorized upload commands in [section 6 of the PyPI guide](PyPI发布准备.en.md#6-dry-run-and-authorized-upload). Keep these distinctions:

- A download mirror is not the upload endpoint. Explicitly use `https://upload.pypi.org/legacy/` and check existing files through `https://pypi.org/simple/`.
- Remove unrelated `UV_PUBLISH_USERNAME`, `UV_PUBLISH_PASSWORD`, `UV_PUBLISH_URL`, `UV_PUBLISH_CHECK_URL`, and `UV_PUBLISH_INDEX` from the publishing child process, and use `--no-config`. Supply the token only through `UV_PUBLISH_TOKEN`; never place it in arguments, Git, logs, or documentation, or enable shell tracing.
- uv does not automatically read `PYPI_TOKEN` as its publishing token. If that is the existing variable, map it to `UV_PUBLISH_TOKEN` inside the publishing process without printing it.
- A dry run establishes neither account authority nor publication. After an interrupted upload, inspect the official file list first. `uv publish` can skip byte-identical existing files; stop on a digest mismatch instead of changing filenames.

## 6. Verify using official data after upload

| Layer | Evidence to retain |
| --- | --- |
| PyPI metadata | Official version JSON: name, version, Python range, MIT, English body, URLs, and extras |
| Actual files | Wheel and sdist listed by JSON / simple; download from returned URLs and match SHA-256 to the validated Release |
| Actual installation | A new independent `.venv`: downloaded wheel, version, import origin, CLI, settings, and resources; install dependencies through the required mirror |
| Rendered page | When accessible, inspect body, images, and language switches; a challenge page or HTTP 200 does not establish this |
| Project navigation | Update Chinese/English README entries and release status; packaged text remains tied to its source commit |

Mirrors can lag behind first publication. RunBridge's first release was available through official JSON and downloads while Aliyun still returned 404. A client challenge does not invalidate API/file/install evidence, but visual acceptance must be reported separately.

Keep private reports in ignored `local/releases/<version>/`, including tag, source/workflow commits, Actions URL, both SHA-256 values, upload/read-back times, installation origin, and unperformed acceptance layers. Exclude tokens, credentials, and private environment material from public releases.

## 7. Troubleshooting and adoption

| Symptom | Check and action |
| --- | --- |
| Local sync passes but CI wants a lock update | Compare `UV_DEFAULT_INDEX`, configured defaults, and lockfile registry; restore the locked source before `--locked` sync instead of relocking an old tag |
| uv cache or credential directory is unwritable | Use a writable temporary `UV_CACHE_DIR`; distinguish directory errors from upload authority and never copy tokens into the repository |
| Artifact Action warns about its old Node runtime | Update the pinned SHA from official Action releases and execute CI; do not republish an existing Release for this |
| PyPI still shows Chinese | Inspect actual METADATA / PKG-INFO and official JSON; fix English readme, summary, and documentation URLs in a new version |
| Local and CI files have matching names but different digests | Compare commits, build inputs, and archive contents; use the verified Release files when transferring to PyPI |
| Upload only reports exit code 0 | Verify the official file list, downloaded digests, and fresh installation; distinguish publication from real business acceptance |

Other projects can reuse the workflow responsibilities and adapt versioning, tests, Python range, extras, CLI, and resources. Copying a publishing YAML alone is insufficient, and RunBridge's browser-test exclusion is not a requirement for another project.
