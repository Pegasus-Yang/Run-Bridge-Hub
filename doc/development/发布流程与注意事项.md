# GitHub Release 与 PyPI 发布流程

简体中文 · [English](发布流程与注意事项.en.md)

本手册整理 RunBridge Hub / Node 已执行的发布流程，供本项目维护及其他 Python 项目迁移参考。先阅读本页了解顺序与注意事项，再按 [GitHub Actions 与 Release](GitHubActions与Release.md)、[PyPI 发布准备](PyPI发布准备.md)执行项目命令。本文不自动授予下一次推送或上传权限。

## 1. 区分三种交付

| 操作 | 触发与权限 | 交付与成功标准 |
| --- | --- | --- |
| 普通 CI | 分支 push / PR，`contents: read` | 测试、构建、安装检查通过；保存 Actions Artifact |
| GitHub Release | `v*` tag，或从 main 手动指定已有 tag；发布任务 `contents: write` | 按标签源码构建，草稿附件回读摘要一致后公开 |
| PyPI | 单独授权上传；使用 PyPI 令牌 | 官方 JSON / simple 索引列出文件，下载摘要及全新环境安装通过 |

当前 GitHub Actions 不上传 PyPI，不需要 PyPI 令牌。`GITHUB_TOKEN` 不能代替 PyPI 令牌；以后若改用 Trusted Publishing，需要另行配置 PyPI 信任关系与 GitHub OIDC 权限。

配套入口与已发布版本示例：

| 项目 | 仓库 | PyPI 分发名 / 示例版本 | 可选依赖 |
| --- | --- | --- | --- |
| Hub | `Pegasus-Yang/Run-Bridge-Hub` | `runbridge-hub` / `0.9.3` | `mcp` |
| Node | `Pegasus-Yang/Run-Bridge-Node` | `runbridge-node` / `0.8.2` | `playwright,visual` |

这两个示例版本已经发布，不要按“新版本”步骤重新创建其 tag 或覆盖发行文件。迁移到其他项目时，按实际源码确定包名、Python 范围、CLI、extras、测试标记和资源文件。

## 2. 先准备英文 PyPI 元数据

PyPI 项目正文取自发行包的描述元数据，不会自动跟随 GitHub README 或仓库 About 更新。在 `pyproject.toml` 的现有 `[project]` 中配置：

```toml
[project]
readme = { file = "README.en.md", content-type = "text/markdown" }
```

同时确认简短 `description` 为英文、默认 `Documentation` 指向英文手册，保留中文 README、中文文档入口和双语切换。MIT、作者、Python 范围与项目 URL 应描述实际项目。

README 的文档、语言切换和图片使用公开绝对 URL；GitHub 文件图片链接可使用 `blob/main/...?...` 的 `raw=true` 形式。架构图使用静态 SVG / 图片，不依赖 PyPI 执行 Mermaid。实际检查链接的状态、类型与内容；不以本地文件存在代替公开链接检查。

构建后核对 wheel 的 `*.dist-info/METADATA` 和源码包的 `PKG-INFO`：`Description-Content-Type` 应为 `text/markdown`，正文应等于构建提交中的 `README.en.md`。使用 `get_payload(decode=True).decode('utf-8')` 读取正文，避免中文语言导航被错误解码。依赖 marker 的单双引号可能被 PyPI 规范化，比较依赖含义时使用 `packaging.requirements.Requirement`。

已经上传的同名文件不能覆盖，删除后也不能重用该文件名。若线上仍是中文说明，本流程采用新版本修正：更新元数据、同步版本、重新构建并发布；不要移动旧 tag、改名旧包或尝试覆盖上传。[PyPI 说明](https://docs.pypi.org/publishing/troubleshooting/)

## 3. 新版本先完成本地验证

1. 同步 `pyproject.toml`、包内 `__version__`、`uv.lock`、当前中英文文档与变更记录；在干净提交上构建，保留原版本和 tag。
2. 用仓库根目录 `.venv` 运行适合本项目的测试，再生成 wheel 与源码包。RunBridge 使用 `pytest tests -q -m 'not browser'`；其他项目应按自己的测试契约选择，不能直接照抄该排除项。
3. 严格检查长描述与元数据，明确 wheel 的包/运行资源和源码包范围；排除 `local/`、凭据、日志、缓存与历史原始证据。
4. 在源码目录外创建全新 `.venv`，分别验证基础安装与 extras、版本、site-packages 来源、CLI 帮助、配置解析和运行资源。安装成功不等于真实服务或浏览器验收。

在对应仓库根目录执行构建：

```bash
uv build --out-dir dist --no-sources -i http://mirrors.aliyun.com/pypi/simple/ --trusted-host mirrors.aliyun.com
```

`uv build` 默认先构建源码包再从源码包构建 wheel；`--no-sources` 检查不依赖本机源码覆盖。随后按 [PyPI 手册](PyPI发布准备.md)对当前两个准确文件运行 `twine check --strict`，并显式提供 `readme-renderer[md]`。不要上传 `dist/*`，其中可能有旧版本。

本地已保存的发行文件不要被后续 main 文档构建覆盖。需要再次校验已发布版本时，在独立的 tag checkout 和新输出目录操作；源码提交、工作流提交与文件摘要分别记录。

## 4. 通过 GitHub Actions 发布 Release

新版本源码提交中应包含 `ci.yml`、可复用 `validate.yml` 和 `release.yml`。按本地发布规范提交并推送后，推送该提交的附注 `v*` tag，触发 Release；分支提交和 PR 只做验证。

工作流先核对标签、元数据、源码与锁文件，再测试、打包、检查并安装实际 wheel。发布任务消费同一次验证产生的 Artifact，不另行构建。外部 Actions 固定提交 SHA；本项目已将上传/下载 Artifact Actions 更新到 Node.js 24 运行时。

已有 tag 早于工作流时，从 **main** 手动运行新版工作流，输入原 tag；工作流单独检出原 tag 源码。默认分支必须已有 `workflow_dispatch`，操作者需要写权限。[GitHub 手动运行说明](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)

```bash
gh workflow run release.yml --repo Pegasus-Yang/Run-Bridge-Hub --ref main -f tag=v0.9.3
gh workflow run release.yml --repo Pegasus-Yang/Run-Bridge-Node --ref main -f tag=v0.8.2
```

以上为历史补发入口示例；这些 Release 已存在，重复运行会按设计停止。没有 `gh` 时可用 Actions → Release → Run workflow，在 main 上填 tag；无需专门创建新的 GitHub 凭据来执行该操作。

Release 自有附件为 wheel、源码包、`SHA256SUMS`、`release-manifest.json`。GitHub 另生成 Source code zip / tar.gz，它们不等于构建后的 Python 源码分发包。Actions Artifact 当前保留 14 天，长期下载使用 Release。

确认验证和发布任务成功、草稿已经公开；回读附件并核对摘要。manifest 的 `source_commit` 必须对应 tag；补发时 `workflow_commit` 可以是较新的 main 提交。遇到已有 Release / 草稿先核对内容，不自动覆盖。

## 5. 将同一份 Release 文件单独发布到 PyPI

若 GitHub Release 已发布，直接复用其 wheel 和源码包。不要从已经改过 README 的 main 重打相同版本。以 Hub 0.9.3 为例，下面仅下载并核验：

```bash
rb_release_dir=$(mktemp -d)
gh release download v0.9.3 --repo Pegasus-Yang/Run-Bridge-Hub --dir "$rb_release_dir"
(cd "$rb_release_dir" && shasum -a 256 -c SHA256SUMS)
```

Node 替换仓库与 tag。核对 manifest 的源码提交和包内英文描述，随后对实际下载的两个包执行严格检查及全新环境安装。发布命令中的两个文件路径应改为下载目录中的准确路径；已核验本地 `dist/` 与 Release 逐字节相同时也可直接使用。

上传前先查 `https://pypi.org/pypi/<分发名>/<版本>/json`：不存在时可首次上传；已存在时对照文件列表和摘要，不能把“名称相同”当作内容一致。

按 [PyPI 发布准备第 6 节](PyPI发布准备.md#6-预演与实际上传)执行预演与授权上传。需要注意：

- 下载镜像不是上传入口。明确使用 `https://upload.pypi.org/legacy/`，以 `https://pypi.org/simple/` 检查已有文件。
- 发布子进程清除其他项目的 `UV_PUBLISH_USERNAME`、`UV_PUBLISH_PASSWORD`、`UV_PUBLISH_URL`、`UV_PUBLISH_CHECK_URL`、`UV_PUBLISH_INDEX`，配合 `--no-config`。令牌只通过 `UV_PUBLISH_TOKEN` 传入，不写入参数、Git、日志或文档，不启用 shell 跟踪。
- `PYPI_TOKEN` 不是 uv 自动读取的发布变量。若环境中只有它，在发布进程内映射成 `UV_PUBLISH_TOKEN`；不要打印其值。
- `--dry-run` 只做预演，不证明账号权限或实际上传成功。上传中断后先检查官方文件列表；`uv publish` 可跳过内容完全相同的已有文件，摘要不同则停止，不换文件名绕过。

## 6. 上传后按官方数据验收

| 检查层级 | 应保留的证据 |
| --- | --- |
| PyPI 元数据 | 官方版本 JSON 中的包名、版本、Python 范围、MIT、英文长描述、项目 URL、extras |
| 实际文件 | JSON / simple 列出 wheel 和源码包；从返回的下载 URL 回读，SHA-256 与已验证 Release 一致 |
| 实际安装 | 新建独立 `.venv` 安装回读的 wheel，验证版本、导入来源、CLI、配置和资源；依赖按项目约定镜像安装 |
| 页面显示 | 能访问网页时检查正文、图片和语言切换；客户端验证页或 HTTP 200 不代表正文已检查 |
| 项目导航 | 确认发布后更新的中英文 README 入口与发布说明准确；包内文案保留构建提交状态 |

镜像首次同步可能延迟，镜像 404 不能推翻官方发布结果。本次 RunBridge 首发遇到过阿里云尚未列出新包，而官方 JSON、下载与安装均已成功。遇到 PyPI 客户端验证页，先用官方 JSON、文件和安装结果确认发布；页面视觉检查应另记结果，不能冒称完成。

原始报告放在忽略的 `local/releases/<版本>/`，记录 tag、源码/工作流提交、Actions URL、两份文件 SHA-256、上传与回读时间、安装来源及未执行的验收层级。不得公开令牌、凭据或私人环境材料。

## 7. 常见问题与迁移

| 现象 | 核对与处理 |
| --- | --- |
| 本地 sync 成功，CI 提示锁文件要更新 | 比较 `UV_DEFAULT_INDEX`、项目默认源与 `uv.lock` 的 registry；恢复锁定来源后 `--locked` 检查，不为旧 tag 临时重锁 |
| uv 缓存或凭据目录不可写 | 使用可写临时 `UV_CACHE_DIR`；环境目录错误与上传权限错误分别诊断，不把令牌拷进仓库 |
| Artifact Action 出现旧 Node 运行时警告 | 根据官方 Action 版本更新固定 SHA，并实际执行 CI；不因此重发或覆盖既有 Release |
| PyPI 仍显示中文 | 检查实际包的 METADATA / PKG-INFO 和官方 JSON，修正英文 readme、summary 与文档 URL 后发布新版本 |
| 本地包与 CI 包同名但摘要不同 | 检查源码提交、构建来源与包含文件；同步到 PyPI 时选择已核验的 Release 原文件 |
| 只得到上传退出码 0 | 补做官方文件列表、下载摘要和独立安装；明确区分发布、安装与真实业务验收 |

其他项目可复用流程和三个工作流的职责划分，按自己的版本机制、测试、Python 范围、extras、CLI 与静态资源修改验证项。不要仅复制一份发布 YAML，也不要把 RunBridge 的浏览器测试排除条件强加给其他项目。

参考：[uv 构建与发布](https://docs.astral.sh/uv/guides/package/)、[PyPI 长描述](https://docs.pypi.org/project-management/project-descriptions/)、[PyPA README 指南](https://packaging.python.org/en/latest/guides/making-a-pypi-friendly-readme/)。
