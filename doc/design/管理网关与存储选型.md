# RunBridge Hub 的管理、网关与存储选型

[文档导航](../README.md) · [节点服务范围与架构](节点服务范围与架构.md)

## 1. 首期确定选择

**RunBridge Hub 的管理与网关在代码职责上分开，首期在同一服务、同一进程部署。Hub 使用 SQLite 与内存；不部署 Redis，也不部署独立数据库服务器。** RunBridge Node 保存少量本地身份与配置即可。

以上选择已由用户确认，R0/R1 已按此实现并通过管理 API 与控制连接验收。原生执行路由尚未实现，当前细节见[实现架构](../architecture/R0与R1实现.md)。

需要持久化不等于需要额外运维一个数据库服务。SQLite 是数据库，但以本地文件形式运行；连接网关的活对象则必须留在其所属进程中。

## 2. 管理和网关是否要拆开

| 方案 | 优点 | 新增成本 | 判断 |
| --- | --- | --- | --- |
| 同进程、分模块 | 连接表、权限撤销、资源占用直接协调，部署简单 | 必须避免阻塞数据库/文件操作 | **首期推荐** |
| 同机器、分进程 | 可分别重启、隔离部分负载 | 内部协议、归属路由、共享协调和故障恢复 | 有实际隔离需求后再做 |
| 独立服务、多网关 | 连接/吞吐可单独扩容和升级 | 跨实例路由、租约、故障转移和运维 | 依据测量与部署需求增加 |

初期分模块即可：管理模块处理登记、凭据、查询和会话规则；网关模块处理连接、帧/HTTP 转发、背压和断开。模块相互调用清晰接口，不把数据库逻辑塞进协议转发循环。

不根据“管理”和“网关”两个名字就部署两个微服务，也不根据节点数单独判断是否拆分。应测量并发执行流、带宽、事件循环延迟、队列占用和管理查询延迟。

## 3. 为什么首期只运行一个 ASGI Worker

活 WebSocket、连接任务和资源级锁属于进程内对象。多个 Worker 的 Python 内存相互独立；客户节点可能连接进程 A，而管理请求和调用方连接落在进程 B，B 无法直接取得 A 的连接对象。

所以首期明确一个实例、一个 ASGI Worker。异步连接并不要求每个节点一个 Worker。[Uvicorn Worker 配置](https://uvicorn.dev/settings/)、[FastAPI 多进程说明](https://fastapi.tiangolo.com/deployment/server-workers/)

用户已确认按 100 用户、10 并发执行规划，每名用户暂按 1 个在线客户端估算。这是基于客户端执行、服务端异步转发的设计目标，容量上限尚未测量；重流量场景和验收方式见[最小实现与验证计划](最小实现与验证计划.md)。连接数本身不是增加 Worker、拆分服务或引入 Redis 的充分理由。

增加多个 Worker 前，要实现节点连接归属、定向路由和跨进程协调。只增加 `--workers`，或只加入 Redis 保存一个节点 ID，都不能解决原生连接的持有与转发问题。

## 4. 持久化、内存和文件各存什么

| 内容 | 推荐位置 | 理由 |
| --- | --- | --- |
| 稳定节点 ID、节点身份验证信息、停用状态 | 服务器 SQLite | 服务器重启后仍可认证和管理 |
| 外部访问凭据验证信息、范围、到期/撤销记录 | 服务器 SQLite | 撤销和许可不能因重启丢失 |
| 资源配置、已知执行能力/版本快照 | SQLite；新鲜状态在内存 | 快照可持久，运行前仍需探测 |
| 会话 ID、归属、状态、创建/结束/异常原因 | SQLite 元数据 | 支持查询和重启协调，不代表会话仍活着 |
| 活 WebSocket、协程、当前路由、资源短期锁 | 服务器进程内存 | 活对象不可序列化后恢复成真实连接 |
| 客户端身份、服务器地址、本地配置 | 客户端本地配置文件 | 数据少、写入频率低 |
| 本地进程对象、浏览器/设备当前占用 | 客户端内存 | 必须以真实资源为准 |
| 录屏、截图与下载附件 | 按会话管理的本地输出目录 | 不将大二进制和每个协议帧写进 SQLite |

首期可有三类核心记录：节点、访问许可、会话元数据。资源配置按实际需要保存，不提前创建通用任务队列、业务运行、模型记录或复杂审计表。

一次创建/释放会话可以更新元数据；原生浏览器命令和高频心跳不应每条落库。最后观察时间可按状态变化或合理频率更新，避免用元数据数据库承担转发日志流。

## 5. 完全不用数据库行不行

| 场景 | 是否可行 | 代价 |
| --- | --- | --- |
| 一次性演示，重启后全部重登记 | 可以只用内存 | 凭据撤销、登记和会话历史可能丢失 |
| 极少量配置、单写者和手工管理 | 可以用 JSON 文件 | 需处理原子替换、并发写、关联更新与备份 |
| 节点长期登记、授权需要跨重启保持 | 需要可靠持久化 | **SQLite 比自建文件存储更合适** |
| 多机器共享写入或较重管理负载 | 使用客户端/服务器数据库 | PostgreSQL 等可作为后续选择 |

因此，数据库不是打通通信的技术前提；但对准备长期使用的最小节点服务，建议从 SQLite 开始。它不增加独立数据库服务的部署成本，同时提供事务与索引。

## 6. SQLite 的边界与异步访问

SQLite 同一数据库文件在同一时刻只有一个写者，适合少量管理元数据和短事务。WAL 可改善读写并行，但仍不提供多写者，也不能把数据库文件放在多机器共享网络目录作为集群数据库。[SQLite 使用场景](https://www.sqlite.org/whentouse.html)、[WAL 限制](https://www.sqlite.org/wal.html)

Python 标准库 `sqlite3` 已提供基础接口。首期可将短数据库操作放到专门线程中，确保连接由适当线程持有并串行访问；不在网关事件循环直接执行慢文件/数据库操作。[Python sqlite3](https://docs.python.org/3.14/library/sqlite3.html)

R1 选择 aiosqlite：它通过每连接共享线程与请求队列减少对主事件循环的阻塞，当前已锁定 0.22.1 并通过 Python 3.14 的登记/许可/快照持久化验证。采用便利库是当前实现选择，不改变 SQLite 与内存的职责边界。[aiosqlite](https://aiosqlite.omnilib.dev/en/stable/)

首期不需要 ORM 或复杂迁移框架。仍需记录数据格式版本，并在有实际字段迁移时维护数据；不把“不用 ORM”理解为可以随意修改已部署数据。

## 7. Redis 是否必需

**单实例、单进程时不必需。** 内存足以保存连接、短期占用和路由；SQLite 保存可靠元数据。Redis 不会保存活 WebSocket 或恢复浏览器对象，不能作为节点断连恢复方案。

| 后续需求 | Redis 可能提供什么 | 仍然必须解决什么 |
| --- | --- | --- |
| 多个网关 | 有期限的在线/连接归属索引 | 请求转到真正持有连接的实例 |
| 跨实例事件 | 通知或消息传递 | 丢消息、顺序、确认和重连行为 |
| 跨实例资源占用 | 原子条件更新/有期限的协调信息 | 旧执行者停止、租约代次与失效处理 |
| 限流/短期缓存 | 共享计数或缓存 | 明确是否确实需要这些功能 |

Redis 只是候选，不是多实例的唯一方案；也可采用数据库协调、定向路由或消息系统。根据需要选一种清晰的组合，不把数据库、Redis、消息队列都作为默认必需项。

Redis Pub/Sub 是 at-most-once，订阅者断线时通知可能丢失，不应把它当作可靠执行指令账本。[Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/)

## 8. 重启后的状态处理

SQLite 保留节点与许可，不能保留在线事实。服务器启动时不根据旧 `RUNNING` 记录立刻认定设备可用；旧会话先标记为待协调，节点重连并报告真实进程/资源后再处理。

首期不支持离线动作排队和透明恢复原生对象。连接失效后返回明确状态，调用方重新查询并取得新会话；涉及外部写入的操作不能因为连接恢复就自动重复执行。

## 9. 引入更多组件的条件

- 写入竞争、跨主机共享元数据或备份运维要求超过 SQLite：评审 PostgreSQL 等数据库服务。
- 长连接/转发负载要求独立扩容或升级：评审管理与网关分服务。
- 已决定多网关且需要共享即时路由/协调：再评审 Redis、消息系统或其他机制。
- 当前需求没有证明这些条件成立：保持单进程、SQLite 与内存的方案。
