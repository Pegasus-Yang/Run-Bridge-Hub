# 类似产品与开源选型

[文档导航](../README.md) · [公开依据与研究边界](../reference/公开依据与研究边界.md)

本次未发现一个经过核验、可直接安装即同时满足多租户 SaaS、云端 AI 决策、客户电脑执行、当前浏览器复用和自有 Android/iOS 设备管理的完整开源产品。**已经存在足够的基础能力，可组合实现；节点接入、租户隔离、生命周期与报告仍需要平台开发。** 这不是断言市场上不存在其他完整产品。

产品主线建议自行开发上述控制与业务职责，直接使用执行 SDK。消息、流程与网络中间件仍有可直接复用的候选，具体分工见[自研边界与中间件选择](自研边界与中间件选择.md)。

最新边界建议将节点部分独立为服务，优先保持原生执行 API；面向 Agent 的简化工具由调用方选择。该建议的接口合同与兼容性要求见[独立节点服务与对外契约](独立节点服务与对外契约.md)，下文工具 RPC 示例仍可作为可选适配路线。

## 1. 商业产品与成熟架构参考

| 产品/方案 | 已核实能力 | 与本需求接近之处 | 差异和证据边界 |
| --- | --- | --- | --- |
| [mabl 本地执行](https://help.mabl.com/hc/en-us/articles/19084071554452-Triggering-tests-from-the-mabl-CLI) | CLI 可在本地/CI 执行 browser、API 测试，另有本地 mobile 命令；本地执行为顺序模式 | 云端测试管理与客户本地执行的产品参考 | 公开资料未证明其内部采用逐动作云端 LLM 控制；本地与云端计划能力不同 |
| [Leapwork Remote Agent](https://docs.leapwork.com/leapwork-flow/latest/working-with-leapwork/agents-overview) | 注册远程执行 Agent，分布执行 Web/桌面/虚拟桌面流程，也能接入 Grid | 中央调度和执行机器分离非常接近 | runtime Agent 指执行服务，不必等同 AI Agent；其部署和端口模型不同于本方案 |
| [BrowserStack Local](https://www.browserstack.com/docs/local-testing/how-local-testing-works) | 本地组件主动建立加密连接，让云端浏览器/设备访问客户内网服务 | 内网接入、用户登记连接和会话管理参考 | 浏览器/设备位于 BrowserStack 云端，不是客户本机浏览器/USB 手机 |
| [Sauce Connect 5](https://docs.saucelabs.com/secure-connections/sauce-connect-5/) | 加密隧道采用 HTTP/2，接入 Sauce 测试环境与客户网络 | 企业网络与云端执行连接的参考 | 主要是网络接入，不能直接等同本机浏览器接管；应研究 5 而非旧 4 方案 |
| [GitHub 自托管 Runner](https://docs.github.com/en/actions/reference/runners/self-hosted-runners) | 用户环境中的 Runner 通过出站连接获取任务 | 节点登记、云端调度、本地执行和更新机制参考 | 是 CI 运行器，不是交互式浏览器工具服务；任务代码通常本地执行 |
| [Selenium Grid](https://www.selenium.dev/documentation/grid/architecture/) | Router、队列、Distributor、Node、Session Map 分工管理远程浏览器会话 | 与用户举的类比直接对应 | 不自带 AI、客户授权 UI 和 SaaS 租户体系；传统部署还要求组件互相可达 |

mabl 的本地计划运行并不具备所有云端计划能力，官方列出并发、阶段等差异。它适合证明产品形态，并不证明云端/本地执行行为完全一致。[mabl 计划执行区别](https://help.mabl.com/hc/en-us/articles/21184963938708-Triggering-plan-runs)

## 2. 最接近“云端 Agent 控制已登录浏览器”的开源基础

| 基础 | 已核实能力 | 可以复用 | 仍要开发/验证 |
| --- | --- | --- | --- |
| [Playwright MCP](https://github.com/microsoft/playwright-mcp/blob/b8b4183e099f136cbec0388a6088d4aa2f6b9685/README.md) + [官方扩展](https://github.com/microsoft/playwright/blob/d9f2fd3e2232ace8e317a84eda6cb86e25bcf49c/packages/extension/README.md) | MCP 工具控制浏览器；扩展连接现有页面及登录状态 | 本机工具执行器、页面观测、现有标签页接入 | SaaS 节点连接、授权范围、资源租约、断线处理；过滤不需要的工具 |
| [Chrome DevTools MCP](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/f08dbe152502d66e75fa07fb2588dc0feb42bc20/docs/advanced-usage.md) | 原生确认连接现有 Chrome，或接入调试端口 | Chrome 144+ 的已有会话接入与调试观测 | Profile 范围较宽；跨网连接、多租户和测试断言不由它完整解决 |
| [Midscene Bridge](https://www.midscenejs.com/bridge-mode) | Chrome 扩展连接桌面浏览器，保留会话；模型配置放在 Node.js 侧 | 视觉 UI 操作、扩展授权流程 | 文档示例不是现成 SaaS 节点链路；要拆开云端模型逻辑与本地设备交互 |
| [browser-use Remote Browser](https://docs.browser-use.com/open-source/customize/browser/remote) | Agent 可配置远程 `cdp_url` | 云端运行浏览器 Agent、连接远程浏览器的入口 | 客户节点出站转接及授权不自动完成；工具 RPC 不能透明替代 CDP |

Midscene 还提供截图和动作接口的自定义接入点，可研究云端 Agent 包装远程设备工具的方式；该接口的存在不证明网络时延、所有手机或已有浏览器模式已被本方案验证。[Midscene 自定义界面接入](https://www.midscenejs.com/integrate-with-any-interface)

建议 Web 产品主路线采用 **自研工具接口 + 节点本地 Playwright**。现有浏览器复用可先使用官方扩展及对应桥接验证，也可单独评审自研桥接；不要求完整 Playwright MCP 成为默认产品运行时。若需要画布或以截图为主的 App 交互，再对 Midscene 的自定义接口做专项验证；如果选择 browser-use，按它实际依赖的 CDP 能力设计适配，不同时维护两套不必要的默认浏览器执行路径。

## 3. 基础设施与移动端

| 方案 | 适用职责 | 本需求中的位置 | 首期建议 |
| --- | --- | --- | --- |
| [Playwright](https://playwright.dev/docs/api/class-browsertype) | 独立浏览器、定位与等待、浏览器协议连接 | 本机 Web 执行器 | 优先 |
| [Appium](https://appium.io/docs/en/latest/guides/security/) + UiAutomator2/XCUITest | Android/iOS 驱动与 WebDriver 接口 | 本机手机执行器 | Android 先验证，iOS 分常规与受限路径 |
| [Selenium Grid](https://www.selenium.dev/documentation/grid/components/) | 浏览器槽位、会话路由和远程 WebDriver | 已有 Selenium 资产的执行适配 | 可接入，不强制让平台完整复制 Grid |
| [frp](https://github.com/fatedier/frp) | NAT 后的反向代理 | 协议通道原型或客户既有网络设施 | 可选；不是租户授权或测试会话管理器 |
| [DeviceFarmer/STF](https://github.com/DeviceFarmer/stf) | 从浏览器管理/控制 Android 设备 | 多设备共享池的参考 | 单个客户 USB 手机不必先建设 STF |
| [Skyvern](https://github.com/Skyvern-AI/skyvern) | AI 浏览器工作流框架 | 浏览器 Agent 的另一个候选 | 评估拆分范围和许可证后再决定 |

Selenium Grid 的 Node 登记后，Distributor 会通过 HTTP 确认 Node 可达；所以“客户端向 Hub 登记”本身不能解决 NAT、客户防火墙与回调可达性。需要保护网络、连接转接或另一种节点传输。[Grid 组件说明](https://www.selenium.dev/documentation/grid/components/)

frp 能证明反向代理机制成熟，但通道打通后仍需授权、租户绑定、协议验证和执行生命周期。不要将其默认公开端口直接用作客户 CDP、ADB 或 Appium 接口。

## 5. 推荐的最小组合

| 层 | 建议 |
| --- | --- |
| 平台 | 沿用现有账户、项目、用例和数据库技术栈；增加异步运行、节点目录和工具网关 |
| AI | 使用能调用受控工具的 Agent；模型与规划在平台；不要求特定模型厂商 |
| 客户端原型 | 自研本地常驻程序，管理身份、出站连接、授权、执行子进程和停止 |
| Web | 本地 Playwright；现有浏览器优先官方扩展；原生 Chrome 确认模式作备选 |
| API | 本地 HTTP 执行器、客户 CA/代理与凭据引用 |
| 移动 | 本地 Appium 与客户选择的驱动/设备；按兼容矩阵登记 |
| 证据 | 平台保存脱敏后的观测与报告；敏感原始数据可按政策留在节点 |

平台与客户端的命令协议优先自研并使用现有 WSS 库。NATS/JetStream、Temporal、frp 为按需候选，不需要先找一个完整测试中间件才能开始，也不需要全部引入。

客户端若以 Node.js 为基础，较容易管理 Playwright 和 Appium 的本地调用；是否采用 Go/Rust 外壳或桌面 UI，等原型确认后结合团队栈决定。无需为了研究结论先引入多套运行时或重写已有平台。
